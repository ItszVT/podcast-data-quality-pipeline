# PostgreSQL foundation (Step 2)

SQLite remains the default local backend and continues to use the existing `requirements.txt`, `src/database.py`, and database file paths. PostgreSQL support is optional and limited to a connection context and explicit schema migrations. Audit persistence and dashboard reads still use SQLite; selecting PostgreSQL in those application entry points fails closed.

## Optional dependency and configuration

From the project root in PowerShell, install the existing dependencies and the PostgreSQL extra only when needed:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip install -r requirements-postgres.txt
```

Configure the backend outside source control. For example, set `PODCAST_DB_BACKEND=postgres` and `PODCAST_DATABASE_URL` in the process environment or a local secret manager. The URL must use `postgresql://` or `postgres://` and include a hostname. Every non-loopback connection requires exactly one `sslmode=verify-full` parameter before the driver is called; missing, empty, repeated, or weaker modes are rejected. This requires both certificate-chain and hostname verification. Loopback connections preserve local PostgreSQL behavior and may use local TLS settings for testing. Errors omit connection details. No connection is attempted merely by importing project modules.

## Explicit migration command

Migrations are never run at dashboard startup. After configuring PostgreSQL and installing the optional dependency, apply migrations explicitly:

```powershell
python -m src.postgres_database migrate
```

The equivalent Python function is `src.postgres_database.migrate_postgres()`. It requires `PODCAST_DB_BACKEND=postgres`, uses a transaction-scoped advisory lock, records applied versions in `schema_migrations`, and returns the versions applied by that call. Re-running it skips versions already recorded. Each migration and its version row are committed in the same transaction; failures roll back the migration transaction. Use only a disposable database for testing this command.

## Schema mapping

`src/db/migrations/v0001_initial_schema.py` defines the initial PostgreSQL schema from the actual SQLite DDL in `src/database.py`. It creates `audit_runs`, `podcast_records`, `data_quality_issues`, and `url_checks`, including the existing primary keys, unique constraints, check constraints, indexes, composite foreign keys, nullable issue `record_id`, and `ON DELETE CASCADE` behavior. Surrogate integer keys use `BIGINT GENERATED BY DEFAULT AS IDENTITY`, preserving generated keys while permitting explicit IDs if a future migration tool needs them.

The SQLite timestamps are stored as ISO text; PostgreSQL uses `TIMESTAMPTZ` so offsets are interpreted as instants and compared correctly. PostgreSQL returns these values in the session timezone, so future persistence/dashboard work must normalize display to UTC and parse timestamps deliberately. SQLite JSON text maps to PostgreSQL `JSON`, not `JSONB`, preserving JSON text/key ordering while adding PostgreSQL JSON validation and operators. Future persistence code must pass parsed JSON or valid serialized JSON; the current SQLite serialization code is unchanged.

## Verification and limitations

Connection setup and migration orchestration have offline unit tests using a fake driver. Actual PostgreSQL DDL, constraints, indexes, foreign keys, migration rollback, and repeat behavior are covered by integration tests. Local loopback testing remains the default and requires `PODCAST_TEST_DATABASE_URL` to point to a database whose name contains `test`. Hosted testing is disabled unless `PODCAST_TEST_ALLOW_REMOTE=1` is explicitly set; it additionally requires the independent `PODCAST_TEST_EXPECTED_HOST`, `PODCAST_TEST_EXPECTED_DATABASE`, and `PODCAST_TEST_EXPECTED_USER` values, plus `sslmode=verify-full` in the URL. Before creating a schema, the fixture verifies the server-reported database and user and confirms the session is encrypted. Each test creates a unique fixture-owned schema; teardown drops only that exact schema after confirming the current user owns it. Use only a dedicated disposable test database with no production or real audit data. Keep the URL in a secret store and never print it. Tests skip when no test URL or psycopg driver is available; mocked tests do not establish PostgreSQL compatibility.

This step does not add PostgreSQL audit persistence, dashboard SQL, data migration, Neon provisioning, or cloud automation. It does not connect to or modify the real SQLite database.

## Test-fixture failure handling

The integration fixture validates its test-only target before importing or connecting the driver, verifies the connected database, user, and (for hosted targets) TLS state before creating a schema, and records the generated schema name only after the schema creation statement succeeds. Teardown receives that exact recorded name and drops only that owned schema; it never retries cleanup with a broader database or schema target. Fixture-level offline tests exercise configuration, identity/TLS rejection, setup failure, test failure, cleanup failure, and prevention of fallback to the application URL. These mocked tests verify fixture control flow only and do not establish PostgreSQL server compatibility.

Cleanup runs in the fixture's `finally` block, but forced process termination or machine shutdown can interrupt Python before that block executes. This can leave a uniquely named temporary schema in the dedicated test database. If an interrupted run occurs, inspect the dedicated test database and identify any orphaned `podcast_pipeline_test_...` schema before manually removing it. Do not run broad cleanup commands or inspect a production database.

## Identity checks on migration connections

The integration fixture verifies the initial connection before creating its temporary schema. `connect_postgres()` now also verifies the actual `current_database()` and `current_user` on the very connection it yields, and checks the live connection's `pg_stat_ssl` state for hosted connections. This check runs before migration code can acquire its lock or execute DDL. The fixture requires `sslmode=verify-full`; that setting is preserved on the separate migration connection, so certificate-chain and hostname verification are performed by psycopg/libpq as well as checking that the active connection is encrypted. Identity or TLS verification errors close the connection and are reported without connection details.
